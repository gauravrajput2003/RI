## Inspected path and executed test

Inspected W15 and GT06 decoders, fixtures and existing capture tests; protocol registry and shared framing; normalized telemetry types; TCP tracker and device resolver; tracker repository and state merge; HTTP boundary and API telemetry handler; API application mounts, repository/latest-location route; existing tracker, API, and PGlite authorization tests.

The new opt-in integration test launches the actual tracker server as a child Node process, binds it to a temporary TCP port, and sends unchanged fixture bytes. It also runs the actual API application on a temporary HTTP port and logs in through the existing authentication service. It uses real pg pools throughout.

Executed flow:

1. Create temporary user, vehicle, device, and active assignment records. Decode the fixture login to obtain identity; no production identifier is invented or substituted. Refuse to overwrite an existing device using that identity.
2. Send login over TCP, exercising the existing framer, configured protocol resolution, device lookup, connection identity, and acknowledgement. Independently assert the real device resolver result.
3. Send the authentic location packet over TCP. The production tracker calls persist(), resolves the active device and assignment, inserts locations, merges device_status, commits, and publishes through HttpTelemetryBoundary.
4. Receive that real HTTP request through the existing internal-secret validation and normalization. A test observation callback at the final publication hook checks that the committed location is visible from the API's independent PostgreSQL pool. Socket.IO delivery itself is not part of this database test.
5. Read the inserted location and current state directly from PostgreSQL, including PostGIS geometry assertions. Fetch latest-location over authenticated HTTP and compare with decoded values.
6. Send the captured heartbeat and replay the unchanged location packet. Verify append-only history, current-state merge behavior, and latest selection by server receive time.
7. Stop test transport processes and delete only the generated test IDs in a transaction. Assert zero remaining rows across all seven touched tables. Cleanup also ran after the initial failed test and a setup-timeout retry.

## Defect found and smallest fix

The first actual PostgreSQL run failed in the production locations INSERT with SQLSTATE 42P08: “could not determine data type of parameter $5”. Coordinate parameters appeared in IS NULL checks without an explicit type. The same pattern existed in the device_status INSERT.

Added `::double precision` to the coordinate parameters in the two existing CASE null-checks. No business-rule expressions, authorization predicates, repositories, schemas, migrations, or architecture were replaced. The corrected test passed through both inserts and subsequent UPSERT updates.

One intermediate retry timed out in setup; cleanup succeeded. A subsequent complete run passed, followed by the final run reported below. No PASS is based on the failed or timed-out runs.

## Persistence and merge behavior

Persistence is owned by the tracker, not by the API telemetry endpoint. persist() executes device resolution/update, active vehicle assignment lookup, locations INSERT, and device_status INSERT ON CONFLICT within one transaction. The API telemetry endpoint publishes normalized committed data; it does not insert it a second time.

The test verifies current-state creation by removing only its temporary status row after login, then sending the first location. It verifies subsequent updates with the actual heartbeat and location replay:

- First location: MOVING, current speed 24, unknown ignition/battery/GSM remain null.
- Captured heartbeat: STOPPED, current ignition false, current speed zero, GSM 4; position and last-location timestamp preserved. No additional location row is inserted.
- Replayed location: MOVING and speed 24; omitted ignition and GSM preserve false and 4 respectively. Last-heartbeat timestamp is preserved; last-location timestamp advances. Battery remains null.

These are existing merge rules, preserved unchanged. In particular, a later location with unknown ignition retains previous false current_ignition while its reported speed and derived state become 24/MOVING. This test records that existing behavior rather than changing it.

Latest-location intentionally reads the newest recorded location for the owned vehicle and active assignment, ordered by server_received_at. It does not read cached coordinates. It joins device_status for the state field. After the heartbeat, the response therefore contains recorded speed 24 and ignition null alongside current state STOPPED. After replay, it returns the newer server timestamp, the unchanged fixture coordinates/tracker timestamp, and MOVING. This existing authorization-era behavior was verified without modifying it.
